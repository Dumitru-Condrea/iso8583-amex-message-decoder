
# API Client Architecture

## 1. Overview

The EMV & Gateway integration provides a set of reusable API clients for interacting with payment tokenisation services.

The implementation uses a shared REST communication layer with dedicated service classes for EMV, Gateway, authentication, and Spring Actuator operations.

All API services are accessed through the centralised `ServiceClients` class, which manages their initialisation and reuse.

The architecture separates common HTTP operations from service-specific functionality, allowing new API operations to be introduced without duplicating request execution, authentication, or logging logic.

## 2. API Client Structure

The API integration consists of the following main components:

| Component | Responsibility |
|---|---|
| RestClient | Executes HTTP requests and processes responses |
| EmvService | Provides EMV API operations |
| GatewayService | Provides Gateway and TGS API operations |
| EmvAuthService | Manages EMV authentication |
| GatewayAuthService | Manages Gateway authentication |
| EmvActuatorService | Provides access to EMV Actuator endpoints |
| GatewayActuatorService | Provides access to Gateway Actuator endpoints |
| WireMockClient | Provides operations for managing WireMock through the EMV Actuator service |

All service clients reuse a single `RestClient` instance provided by `ServiceClients`.

## 3. Shared REST Client

### 3.1 Purpose

`RestClient` provides the common HTTP communication infrastructure used by the API services.

It is built on RestAssured and centralises request execution, response mapping, logging, and Scenario Context integration.

The client supports the following HTTP methods:

- GET
- POST
- PUT
- PATCH
- DELETE

Each operation accepts an `ApiRequest` or an `ApiRequest.Builder`.

### 3.2 Request Execution

All HTTP operations are processed through a common execution mechanism.

The general execution flow is:

1. Receive the prepared API request.
2. Apply request parameters, headers, authentication, and body.
3. Execute the HTTP operation using RestAssured.
4. Map the result into `ApiResponse`.
5. Log the request, response, and execution duration.
6. Register the API exchange in Scenario Context when tracking is enabled.
7. Return the API response to the calling service.

If a runtime exception occurs during execution, the error is logged and propagated to the caller.

**Note:** A completed HTTP exchange may be registered in Scenario Context even when the HTTP status code indicates an API error, such as 400 or 500.

### 3.3 Shared Infrastructure

The `RestClient` instance is created centrally and reused by all supported services.

It is configured with:

| Dependency | Purpose |
|---|---|
| ApiLogger | Request, response, and error logging |
| ApiContext | Automatic API exchange tracking |
| ApiResponseMapper | Conversion of HTTP responses into ApiResponse |

This ensures consistent HTTP communication across EMV, Gateway, Authorization, and Actuator operations.

## 4. EMV Service

### 4.1 Purpose

`EmvService` provides a dedicated interface for interacting with EMV API endpoints.

It encapsulates service-specific operations while delegating HTTP execution to the shared `RestClient`.

The service uses its associated authorization component to obtain the authentication information required for protected endpoints.

### 4.2 Service Access

The EMV service is obtained through `ServiceClients`:

```java
import static com.barclaycard.systemtest.emv.gateway.services.ServiceClients.*;

EmvService emvService = EMV();
```

The same service instance is reused across calls.

### 4.3 Responsibilities

The main responsibilities of `EmvService` include:

- Providing EMV-specific API operations.
- Preparing requests using the common request infrastructure.
- Resolving EMV endpoint URLs.
- Applying authentication where required.
- Returning responses through the common `ApiResponse` model.

## 5. Gateway Service

### 5.1 Purpose

`GatewayService` provides access to Gateway API operations, including functionality used for payment tokenisation testing and TGS configuration updates.

It follows the same architectural approach as `EmvService`, using the shared REST infrastructure and its dedicated authorization service.

### 5.2 Service Access

```java
import static com.barclaycard.systemtest.emv.gateway.services.ServiceClients.*;

GatewayService gatewayService = GATEWAY();
```

### 5.3 Responsibilities

The main responsibilities of `GatewayService` include:

- Executing Gateway-specific API operations.
- Handling tokenisation-related requests.
- Updating token owner configuration through TGS endpoints.
- Applying Gateway authentication.
- Returning standardised API responses.

Higher-level operations, such as TGS configuration updates followed by MongoDB validation, are coordinated by `TgsConfigurationManager`.

This keeps service-specific HTTP communication separate from configuration management and validation logic.

## 6. Authorization Services

### 6.1 Overview

EMV and Gateway use dedicated authentication services.

| Component | Responsibility |
|---|---|
| AuthClient | Provides common authentication-related API communication |
| AuthService | Provides shared authentication workflow functionality |
| EmvAuthService | Manages EMV-specific authentication and JWT caching |
| GatewayAuthService | Manages Gateway-specific authentication and JWT caching |

Both authentication services reuse the common REST communication infrastructure.

### 6.2 Authentication Flow

The authentication workflow includes the following operations:

1. Obtain a master access token.
2. Create an API client using the master token.
3. Create an identity associated with the client.
4. Obtain the final access token for authenticated service operations.
5. Cache the resulting JWT for subsequent requests.

EMV and Gateway maintain separate final JWT caches.

### 6.3 JWT Caching

Authentication tokens are cached to avoid repeating the complete authentication workflow for every API request.

The cache uses token expiration information returned by the authentication service, including `expires_in`, to determine when a new token is required.

While a cached token remains valid, the corresponding service can reuse it for subsequent requests.

When the token is no longer valid for reuse, the authentication workflow is executed again.

### 6.4 Credential Security

Credentials required by the authentication services are stored in encrypted form in the framework configuration.

Dedicated configuration and decryption utilities provide the credentials required during authentication.

Sensitive authentication information must not be exposed in request logs or documentation examples.

Authentication requests are also excluded from automatic Scenario Context tracking.

## 7. Actuator Services

### 7.1 Overview

The framework provides dedicated clients for interacting with Spring Actuator endpoints.

| Service | Purpose |
|---|---|
| EmvActuatorService | EMV Actuator operations |
| GatewayActuatorService | Gateway Actuator operations |

Both services reuse the shared `RestClient`.

### 7.2 Service Access

```java
EmvActuatorService emvActuator = EMV_ACTUATOR();

GatewayActuatorService gatewayActuator = GATEWAY_ACTUATOR();
```

Actuator clients provide technical operations used by framework utilities and test environment management.

For example, Gateway Actuator cache operations are used as part of the TGS configuration update lifecycle.

## 8. WireMock Client

`WireMockClient` is a dedicated client for operations related to WireMock configuration.

Unlike EMV and Gateway services, it uses `EmvActuatorService` for the underlying API communication.

### Service Access

```java
WireMockClient wireMock = WIREMOCK();
```

The client is used by the WireMock state management functionality to control the required test environment configuration.

The complete scenario lifecycle, including Cucumber tags and automatic state restoration, is documented in **WireMock Integration & State Management**.

## 9. Endpoint Management

### 9.1 ServiceUrls

API endpoints are centrally defined in `ServiceUrls`.

The interface groups endpoint definitions into service-specific enums:

| Endpoint Group | Purpose |
|---|---|
| Emv | EMV API endpoints |
| Gateway | Gateway API endpoints |
| Identity | Authentication and identity endpoints |
| EmvActuator | EMV Actuator endpoints |
| GatewayActuator | Gateway Actuator endpoints |

Each endpoint definition provides its URI through the common `ServiceUrls` interface.

This approach avoids scattering endpoint paths across service implementations.

### 9.2 ServiceUrlBuilder

`ServiceUrlBuilder` constructs service URLs using configuration values.

URL generation takes into account:

- The configured base URL template.
- The required service.
- The selected AWS instance number.
- Service-specific port configuration, where applicable.

This allows the same service implementations to operate against different configured environments.

### 9.3 ApiConfig

`ApiConfig` provides access to the configuration values required by API services.

The configuration includes:

- Service URL templates.
- AWS instance information.
- Authentication-related settings.
- Encrypted credentials.
- Service-specific properties.

Centralising these values avoids embedding environment-specific information directly in the API client implementations.

## 10. Usage Guidelines

When implementing new API operations, follow the existing architecture:

1. Define the endpoint in the appropriate `ServiceUrls` enum.
2. Add the required JSON request template, when applicable.
3. Implement the operation in the corresponding service class.
4. Reuse the shared `RestClient` for HTTP execution.
5. Apply the existing authentication mechanism where required.
6. Return an `ApiResponse` and rely on the common logging and Context tracking infrastructure.

Avoid creating additional `RestClient` instances or duplicating authentication logic in Step Definitions.

## 11. Summary

The API client architecture provides a reusable and consistent approach to interacting with EMV, Gateway, and supporting technical services.

A shared `RestClient` handles HTTP communication, while dedicated service clients expose operations relevant to their respective APIs.

Centralised endpoint definitions, environment configuration, authentication management, logging, and Scenario Context integration allow test scenarios to focus on business behaviour rather than repeated infrastructure logic.

Detailed request construction, JSON template handling, and response processing are covered in the following chapter: **Request & Response Management**.
