
# Request & Response Management

## 1. Overview

The EMV & Gateway integration provides a unified approach to preparing HTTP requests, processing API responses, and managing reusable JSON payloads.

The implementation is built around four main components:

| Component | Responsibility |
|---|---|
| `ApiRequest` | Defines HTTP request configuration using a Builder |
| `ApiResponse` | Provides a standard representation of HTTP responses |
| `ServiceRequests` | Defines and loads reusable JSON request templates |
| `RestClient` | Executes HTTP requests using RestAssured |

These components allow API services to prepare requests and process responses consistently without duplicating common HTTP functionality.

## 2. ApiRequest

### 2.1 Purpose

`ApiRequest` represents the configuration required to execute an HTTP request.

It provides a Builder-based API for defining HTTP headers, request parameters, authentication, payloads, and Scenario Context tracking.

The request is constructed before execution and passed to the shared `RestClient`.

### 2.2 Supported Request Properties

| Property | Description |
|---|---|
| Headers | Custom HTTP headers |
| Path Parameters | Values substituted into endpoint paths |
| Query Parameters | Parameters appended to the URL |
| Form Parameters | Form-based request data |
| Multipart Parameters | Multipart request data |
| Body | Request payload |
| Basic Authentication | Username and password |
| Bearer Authentication | Access token |
| Context Tracking | Controls whether the request is recorded in Scenario Context |

These properties are applied to the RestAssured `RequestSpecification` by the shared REST client.

### 2.3 Builder Pattern

`ApiRequest` uses a fluent Builder for constructing HTTP requests.

A new Builder is created through:

```java
ApiRequest.with()
```

The Builder supports the following methods:

| Method | Purpose |
|---|---|
| `header(name, value)` | Adds an HTTP header |
| `pathParam(name, value)` | Adds a path parameter |
| `queryParam(name, value)` | Adds a query parameter |
| `formParam(name, value)` | Adds a form parameter |
| `multipart(name, value)` | Adds a multipart parameter |
| `body(body)` | Sets the request body |
| `basicAuth(username, password)` | Configures Basic authentication |
| `bearerAuth(token)` | Configures Bearer authentication |
| `randomCorrelationId()` | Generates a unique correlation ID header |
| `jsonContentType()` | Sets the JSON Content-Type header |
| `tokenOwnerId(id)` | Sets the `tokenOwnerId` path parameter |
| `brand(name)` | Sets the `brand` path parameter |
| `skipContextTracking()` | Disables automatic Context tracking |
| `build()` | Creates an `ApiRequest` |

#### Example

```java
ApiRequest request = ApiRequest.with()
        .bearerAuth(token)
        .tokenOwnerId(tokenOwnerId)
        .randomCorrelationId()
        .jsonContentType()
        .body(payload)
        .build();
```

The Builder provides a readable way to prepare requests without manually constructing RestAssured specifications.

### 2.4 Authentication

`ApiRequest` supports both Basic and Bearer authentication.

**Basic Authentication**

```java
ApiRequest request = ApiRequest.with()
        .basicAuth(username, password)
        .build();
```

**Bearer Authentication**

```java
ApiRequest request = ApiRequest.with()
        .bearerAuth(token)
        .build();
```

The Builder ensures that only one authentication mechanism is active at a time.

Calling `basicAuth()` clears the previously configured Bearer token.

Calling `bearerAuth()` clears the previously configured Basic authentication credentials.

### 2.5 Convenience Methods

The Builder provides several helper methods for commonly used request properties.

**Correlation ID**

```java
ApiRequest request = ApiRequest.with()
        .randomCorrelationId()
        .build();
```

This generates a UUID and adds it to the `X-Xe-CorrelationId` HTTP header.

**JSON Content-Type**

```java
ApiRequest request = ApiRequest.with()
        .jsonContentType()
        .build();
```

This sets the `Content-Type` header to `application/json`.

**Token Owner ID**

```java
ApiRequest request = ApiRequest.with()
        .tokenOwnerId(tokenOwnerId)
        .build();
```

This adds the `tokenOwnerId` path parameter.

**Card Brand**

```java
ApiRequest request = ApiRequest.with()
        .brand("AMEX")
        .build();
```

This adds the `brand` path parameter.

These helper methods reduce repeated request configuration across API service implementations.

### 2.6 Reusing Request Configuration

`ApiRequest` supports creating a new Builder based on an existing request through the `adjustWith()` method.

This allows existing headers, parameters, authentication settings, request body, and Context tracking configuration to be reused while modifying selected properties.

```java
ApiRequest original = ApiRequest.with()
        .bearerAuth(token)
        .tokenOwnerId(tokenOwnerId)
        .build();

ApiRequest modified = original.adjustWith()
        .header("X-Custom-Header", "value")
        .build();
```

The original request remains unchanged when Builder properties are modified.

The Builder copies the parameter maps, while the request body is reused by reference.

Mutable request bodies, such as Jackson `ObjectNode`, should therefore be handled carefully.

### 2.7 Context Tracking

By default, Context tracking is enabled for newly created requests.

After a completed HTTP exchange, the shared `RestClient` automatically registers the request and response in `ApiContext`.

Technical operations can explicitly disable this behaviour.

```java
ApiRequest request = ApiRequest.with()
        .bearerAuth(token)
        .body(payload)
        .skipContextTracking()
        .build();
```

This is particularly useful for:

- Authentication requests.
- Internal service operations.
- Technical requests that should not appear in the scenario API history.

The complete tracking mechanism is described in the **Scenario Context** chapter.

## 3. ApiResponse

### 3.1 Purpose

`ApiResponse` provides a standard representation of HTTP responses returned by API services.

It allows test implementations to inspect response information without interacting directly with RestAssured for common operations.

The response is created through `ApiResponseMapper` after HTTP execution.

### 3.2 Response Structure

`ApiResponse` contains the following information:

| Property | Type | Description |
|---|---|---|
| `headers` | `Map<String, List<String>>` | HTTP response headers |
| `statusCode` | `int` | HTTP response status |
| `body` | `String` | Response body |
| `raw` | `Response` | Original RestAssured response |

The standard response properties are accessible through Lombok-generated getters.

The original RestAssured response is exposed through the dedicated `raw()` method.

### 3.3 Response Status Validation

`ApiResponse` provides convenience methods for checking HTTP status codes.

| Method | Behaviour |
|---|---|
| `isSuccessful()` | Returns `true` for status codes from 200 to 299 |
| `isUnsuccessful()` | Returns `true` for status codes of 300 or higher |
| `getStatusCode()` | Returns the HTTP status code |

Example:

```java
ApiResponse response = GATEWAY()
        .changeTokenOwnerState(tokenOwnerId, request);

if (response.isSuccessful()) {
    // Process successful response
}
```

For operations requiring a specific HTTP status, the status code can be checked directly.

```java
assertThat(response.getStatusCode()).isEqualTo(200);
```

### 3.4 Response Headers

Response headers are available through `getHeaders()`.

For retrieving an individual header, `ApiResponse` provides:

```java
getHeadersByName(String name)
```

The method returns the first value associated with the specified header name, or `null` if no value is available.

Example:

```java
String contentType = response.getHeadersByName("Content-Type");
```

### 3.5 JSON Response Handling

The `json()` method parses the response body into a Jackson `JsonNode`.

```java
JsonNode json = response.json();
```

Individual JSON properties can be accessed using Jackson methods.

Example:

```java
String token = response.json()
        .at("/emvData/token")
        .asText();
```

This approach is useful when only selected response fields are required.

### 3.6 Mapping Responses to Java Objects

`ApiResponse` also supports deserializing response bodies into Java objects.

```java
<T> T as(Class<T> type)
```

Example:

```java
MyResponse responseBody = response.as(MyResponse.class);
```

This is useful when working with structured responses represented by dedicated Java models.

### 3.7 Accessing the Original RestAssured Response

For advanced use cases, the original RestAssured response is available through:

```java
Response rawResponse = response.raw();
```

This allows access to additional RestAssured functionality when necessary.

Common API operations should use the standard `ApiResponse` methods whenever possible.

## 4. ServiceRequests — JSON Template Management

### 4.1 Purpose

`ServiceRequests` provides centralised access to reusable JSON request templates.

Instead of constructing large JSON payloads directly in Java, request bodies are maintained as resource files.

This simplifies request preparation and allows different scenarios to reuse the same template with different values.

### 4.2 Resource Structure

JSON templates are stored under:

`src/test/resources/testdata/requests/`

The current resource organisation includes:

```text
testdata/
└── requests/
    ├── auth/
    │   ├── emv-identity.json
    │   └── gateway-identity.json
    ├── emv/
    └── gateway/
        ├── change-token-owner-state.json
        ├── get-or-create-token.json
        └── notification-token-update.json
```

Each template is associated with a corresponding enum constant in `ServiceRequests`.

### 4.3 ServiceRequests Interface

The `ServiceRequests` interface defines a common contract for loading JSON templates.

Request definitions are grouped into service-specific enums:

- `Emv`
- `Gateway`
- `Identity`

Each enum constant refers to a corresponding JSON resource file.

For example:

| Request Definition | Resource |
|---|---|
| `CHANGE_TOKEN_OWNER_STATE_REQUEST` | `gateway/change-token-owner-state.json` |
| `GET_OR_CREATE_TOKEN_REQUEST` | `gateway/get-or-create-token.json` |
| `NOTIFICATION_TOKEN_UPDATE_REQUEST` | `gateway/notification-token-update.json` |
| `EMV_IDENTITY_REQUEST` | `auth/emv-identity.json` |
| `GATEWAY_IDENTITY_REQUEST` | `auth/gateway-identity.json` |

### 4.4 Available Template Methods

`ServiceRequests` provides several methods for loading JSON resources.

| Method | Return Type | Purpose |
|---|---|---|
| `asString()` | `String` | Loads JSON as text |
| `asJsonNode()` | `JsonNode` | Loads JSON as a Jackson tree |
| `asObjectNode()` | `ObjectNode` | Loads JSON as a mutable object |
| `as(Class<T> type)` | `T` | Deserializes JSON into a Java object |
| `with(Consumer<ObjectNode>)` | `ObjectNode` | Loads and modifies a JSON template |

### 4.5 Reading a JSON Template

A request can be loaded directly as an `ObjectNode`.

```java
ObjectNode request = ServiceRequests.Gateway
        .CHANGE_TOKEN_OWNER_STATE_REQUEST
        .asObjectNode();
```

This is useful when the original JSON template already contains the required values.

### 4.6 Modifying a JSON Template

The `with()` method accepts a `Consumer<ObjectNode>`.

The modifier is applied to the loaded JSON object before it is returned.

Example:

```java
ObjectNode request = ServiceRequests.Gateway
        .CHANGE_TOKEN_OWNER_STATE_REQUEST
        .with(json -> {
            json.put("scheme", "AMEX");

            json.withObject("/emvSettings")
                    .put("emvTokenisationEnabled", true)
                    .put("exposeTokenToMerchant", false);
        });
```

The method performs the following operations:

1. Loads the corresponding JSON template.
2. Creates an `ObjectNode` representation.
3. Applies the provided modifications.
4. Returns the resulting JSON object.

The original JSON resource file remains unchanged.

### 4.7 Removing JSON Sections

The same mechanism can be used to remove unnecessary sections from a request.

Example:

```java
ObjectNode request = ServiceRequests.Gateway
        .CHANGE_TOKEN_OWNER_STATE_REQUEST
        .with(json -> {
            json.put("scheme", "AMEX");

            json.withObject("/emvSettings")
                    .put("emvTokenisationEnabled", true)
                    .put("exposeTokenToMerchant", false);

            json.remove("digitalWalletsSettings");
        });
```

This is particularly useful when an API request should contain only the configuration section being updated.

### 4.8 Using Templates Without Modifications

When no changes are required, a template can be loaded directly.

```java
ObjectNode request = ServiceRequests.Gateway
        .GET_OR_CREATE_TOKEN_REQUEST
        .asObjectNode();
```

Alternatively, an empty modifier can be used:

```java
ObjectNode request = ServiceRequests.Gateway
        .GET_OR_CREATE_TOKEN_REQUEST
        .with(json -> {});
```

Both approaches allow reuse of existing JSON templates.

## 5. RestClient — Request Execution

### 5.1 Purpose

`RestClient` provides the common HTTP execution infrastructure used by EMV, Gateway, Authorization, and Actuator services.

It is built on RestAssured and centralises request preparation, execution, response mapping, logging, and Scenario Context integration.

### 5.2 Supported HTTP Methods

The client supports:

| Method | Description |
|---|---|
| GET | Retrieves resources |
| POST | Creates or submits resources |
| PUT | Updates resources |
| PATCH | Applies partial updates |
| DELETE | Deletes resources |

Each operation accepts either:

- A completed `ApiRequest`.
- An `ApiRequest.Builder`, which is built before execution.

All operations delegate to the shared internal execution method.

### 5.3 Request Execution Lifecycle

The common execution mechanism performs the following operations:

1. Applies the request configuration to RestAssured.
2. Resolves the target URL.
3. Logs the outgoing request.
4. Executes the HTTP operation.
5. Converts the RestAssured response into `ApiResponse`.
6. Logs the response and execution duration.
7. Registers the API exchange in Scenario Context when tracking is enabled.
8. Returns the resulting `ApiResponse`.

### 5.4 Request Specification

The request configuration is applied to a RestAssured `RequestSpecification`.

Depending on the prepared `ApiRequest`, the client configures:

- Headers.
- Path parameters.
- Query parameters.
- Form parameters.
- Multipart parameters.
- Request body.
- Basic or Bearer authentication.

If a request body is provided, the client prepares it for submission using the common request handling logic.

### 5.5 Response Mapping

The REST client uses `ApiResponseMapper` to transform the original RestAssured response into `ApiResponse`.

This provides consistent response access across all API services.

### 5.6 Exception Handling

If a `RuntimeException` occurs during request execution:

1. The elapsed execution time is calculated.
2. The error is passed to `ApiLogger`.
3. The original exception is rethrown.

Execution exceptions are not silently suppressed.

An HTTP response with a non-successful status code is still a completed HTTP exchange.

Such a response can be registered in Scenario Context when request tracking is enabled.

## 6. Request and Response Logging

`RestClient` uses the shared `ApiLogger` to record HTTP communication.

Logging includes:

- HTTP method and endpoint.
- Request information.
- Response status and body.
- Execution duration.
- Errors during request execution.

Sensitive values are handled through the framework's logging and masking functionality.

Logging behaviour and error diagnostics are described in **Logging & Error Handling**.

## 7. Practical Example

The following example demonstrates how a reusable JSON template can be modified and submitted through the Gateway service.

```java
import com.fasterxml.jackson.databind.node.ObjectNode;

import static com.barclaycard.systemtest.emv.gateway.services.ServiceClients.GATEWAY;
import static com.barclaycard.systemtest.emv.gateway.api.config.ServiceRequests.Gateway.CHANGE_TOKEN_OWNER_STATE_REQUEST;

ObjectNode request = CHANGE_TOKEN_OWNER_STATE_REQUEST.with(json -> {
    json.put("scheme", "AMEX");

    json.withObject("/emvSettings")
            .put("emvTokenisationEnabled", true)
            .put("exposeTokenToMerchant", false);

    json.remove("digitalWalletsSettings");
});

ApiResponse response = GATEWAY()
        .changeTokenOwnerState(tokenOwnerId, request);

assertThat(response.isSuccessful()).isTrue();
```

This example demonstrates:

- Loading a reusable JSON request template.
- Modifying selected JSON fields.
- Removing an unnecessary JSON section.
- Submitting the request through a service client.
- Validating the HTTP response.

For configuration updates requiring MongoDB verification and conditional waiting, use the dedicated `TgsConfigurationManager`, described in **TGS Configuration Management & Validation**.

## 8. Summary

The Request & Response Management layer provides a consistent mechanism for preparing and executing HTTP operations.

`ApiRequest` encapsulates request configuration and supports reusable Builder-based construction.

`ApiResponse` provides standardised access to HTTP results, JSON parsing, Java object mapping, and the original RestAssured response.

`ServiceRequests` allows JSON templates to be loaded and modified dynamically.

Together with the shared `RestClient`, these components simplify API integration and reduce duplicated implementation across test scenarios.

The next chapter, **Scenario Context**, describes how API exchanges and additional scenario-related values are stored, retrieved, and managed during test execution.
