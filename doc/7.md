
# Scenario Context

## 1. Overview

The EMV & Gateway integration provides a centralised Scenario Context for storing and retrieving information generated during test execution.

The `ApiContext` component supports two main capabilities:

- **API Exchange Tracking** — automatically records HTTP requests and their corresponding responses.
- **Test Data Storage** — stores additional objects that can be shared between different steps within the same scenario.

This allows test implementations to access previously executed operations without manually passing request and response objects between Step Definitions.

The Context is integrated with the shared `RestClient` and is accessible through the centralised `ServiceClients` class.

## 2. Main Components

The Scenario Context implementation consists of three main components.

| Component | Responsibility |
|---|---|
| `ApiContext` | Manages API exchange history and additional test values |
| `ApiExchange` | Represents a recorded request/response pair with associated keys |
| `TestContextKey` | Defines keys used to store and retrieve additional test data |

**Package:**

`com.barclaycard.systemtest.emv.gateway.services.scenario.context`

### 2.1 Accessing the Context

The Context is exposed through `ServiceClients`:

```java
import static com.barclaycard.systemtest.emv.gateway.services.ServiceClients.context;

ApiContext context = context();
```

The same Context instance is reused by the framework and its supporting components.

Its stored data is automatically cleared after each Cucumber scenario.

## 3. Automatic API Exchange Tracking

### 3.1 How Tracking Works

The shared `RestClient` automatically records completed HTTP exchanges when Context tracking is enabled for the request.

Each recorded exchange contains:

- The original `ApiRequest`.
- The corresponding `ApiResponse`.
- An endpoint key used to identify the operation.
- Optional additional keys assigned during test execution.

The execution flow is:

1. An API service prepares and executes an HTTP request.
2. `RestClient` receives the HTTP response.
3. The response is converted into `ApiResponse`.
4. If Context tracking is enabled, the request and response are registered in `ApiContext`.
5. The exchange becomes available to subsequent test steps.

API exchanges are stored in execution order.

### 3.2 Tracking Behaviour

Context tracking is enabled by default for newly created `ApiRequest` instances.

This means EMV and Gateway API operations are automatically recorded unless tracking is explicitly disabled.

A successfully completed HTTP call is recorded regardless of whether its HTTP status indicates success or failure.

For example, an HTTP 400 response can still be stored in Context because the HTTP exchange itself completed.

If request execution throws a runtime exception before an `ApiResponse` is available, the exchange is not registered.

### 3.3 Excluding Technical Requests

Technical operations can be excluded from automatic Context tracking.

This is particularly useful for authentication and infrastructure-related API calls.

```java
ApiRequest request = ApiRequest.with()
        .bearerAuth(token)
        .skipContextTracking()
        .build();
```

The `skipContextTracking()` method disables tracking for the corresponding request.

Authentication requests use this mechanism to avoid storing sensitive authentication exchanges in the scenario history.

## 4. ApiExchange

### 4.1 Purpose

`ApiExchange` represents a single recorded API interaction.

It contains the request, response, and a collection of keys associated with the exchange.

| Field | Type | Description |
|---|---|---|
| `request` | `ApiRequest` | Original HTTP request |
| `response` | `ApiResponse` | Corresponding HTTP response |
| `keys` | `Set<Enum<?>>` | Endpoint and additional logical keys |

The request and response can be retrieved through the Lombok-generated getters.

### 4.2 Exchange Keys

When an exchange is registered, it receives an initial key associated with its endpoint.

Additional keys can be assigned later to make the exchange accessible under different logical identifiers.

An exchange can therefore be associated with multiple keys without duplicating its request or response.

These keys are used by the Context to filter and retrieve exchanges.

## 5. Retrieving the Latest API Exchange

### 5.1 Last Exchange

The `last()` method returns the most recently recorded API exchange.

```java
ApiExchange exchange = context().last();
```

The result can be used to access the request and response:

```java
ApiExchange exchange = context().last();

if (exchange != null) {
    ApiRequest request = exchange.getRequest();
    ApiResponse response = exchange.getResponse();
}
```

If no exchanges have been recorded, `last()` returns `null`.

### 5.2 Last Exchange by Key

The `last(Enum<?> key)` method retrieves the most recent exchange associated with a particular endpoint or logical key.

```java
ApiExchange exchange = context().last(
        ServiceUrls.Gateway.GET_OR_CREATE_TOKEN
);
```

This is useful when a scenario executes multiple API operations and a test step needs to access the latest result of a specific operation.

The method searches the recorded exchanges from newest to oldest.

If no matching exchange exists, it returns `null`.

### 5.3 Required Exchange

When an exchange must exist, the Context provides:

```java
context().requireLast();
context().requireLast(key);
```

Unlike `last()`, these methods throw an `IllegalStateException` when no matching exchange is found.

For example:

```java
ApiResponse response = context()
        .requireLast(ServiceUrls.Gateway.GET_OR_CREATE_TOKEN)
        .getResponse();
```

Use `requireLast()` when the absence of an expected API exchange should fail the test immediately.

## 6. API Exchange History

### 6.1 Complete History

The `history()` method returns all recorded API exchanges.

```java
List<ApiExchange> exchanges = context().history();
```

The returned list preserves the order in which exchanges were registered.

It is a new list containing references to the existing exchange objects.

### 6.2 History by Key

To retrieve exchanges associated with a specific endpoint or logical key:

```java
List<ApiExchange> exchanges = context().history(
        ServiceUrls.Gateway.GET_OR_CREATE_TOKEN
);
```

This is useful when the same endpoint is called multiple times during a scenario.

For example, a test can compare responses from consecutive operations.

### 6.3 Requests and Responses

The Context also provides direct access to request and response history.

| Method | Description |
|---|---|
| `requests()` | Returns all recorded requests |
| `requests(key)` | Returns requests matching the specified key |
| `responses()` | Returns all recorded responses |
| `responses(key)` | Returns responses matching the specified key |

Example:

```java
List<ApiResponse> responses = context().responses(
        ServiceUrls.Gateway.GET_OR_CREATE_TOKEN
);
```

These methods simplify access when only requests or responses are required instead of complete `ApiExchange` objects.

## 7. Additional Exchange Tags

### 7.1 Purpose

The Context supports assigning additional logical keys to previously recorded API exchanges.

This is useful when an exchange needs to be identified by a business-related meaning rather than only its original endpoint.

### 7.2 Tagging the Latest Exchange

The `tag(Enum<?> tag)` method assigns an additional key to the latest recorded exchange.

```java
context().tag(MyExchangeTag.TOKEN_CREATION);
```

The tag is added to the existing `ApiExchange`.

No new exchange is created.

### 7.3 Tagging an Exchange by Source Key

An additional overload allows a tag to be assigned to the latest exchange matching a specified source key.

```java
context().tag(
        ServiceUrls.Gateway.GET_OR_CREATE_TOKEN,
        MyExchangeTag.TOKEN_CREATION
);
```

This allows a specific API operation to be tagged even when another request has been executed afterward.

### 7.4 Retrieving Tagged Exchanges

Tagged exchanges can be retrieved using the same methods as endpoint-based exchanges.

```java
ApiExchange exchange = context()
        .requireLast(MyExchangeTag.TOKEN_CREATION);
```

The same tag can also be used with `history()`, `requests()`, and `responses()`.

**Note:** The example `MyExchangeTag` is illustrative. Actual tags can be defined using an appropriate enum.

## 8. Storing Additional Test Data

### 8.1 Purpose

In addition to API exchanges, `ApiContext` provides a separate storage mechanism for arbitrary Java objects.

Values are stored using `TestContextKey`.

This allows different Step Definitions to exchange data without introducing additional shared fields or manually passing objects between methods.

The storage uses:

```java
Map<TestContextKey, Object>
```

### 8.2 Saving Values

Use `put()` to store a value:

```java
context().put(TestContextKey.MY_KEY, tokenOwnerId);
```

The value can be retrieved later in the same scenario.

### 8.3 Nullable Retrieval

The `get()` method retrieves a stored value and validates its expected type.

```java
String tokenOwnerId = context().get(
        TestContextKey.MY_KEY,
        String.class
);
```

If no value exists for the key, the method returns `null`.

If the stored value does not match the requested Java type, an `IllegalStateException` is thrown.

### 8.4 Required Retrieval

Use `require()` when a stored value must exist.

```java
String tokenOwnerId = context().require(
        TestContextKey.MY_KEY,
        String.class
);
```

If the value is missing, the method throws an `IllegalStateException`.

An overload also allows a custom failure message:

```java
String tokenOwnerId = context().require(
        TestContextKey.MY_KEY,
        String.class,
        "Token Owner ID was not stored in Scenario Context"
);
```

The custom message makes failed test diagnostics easier to understand.

**Note:** Replace `MY_KEY` with an actual constant defined in `TestContextKey`.

## 9. Working with Lists

### 9.1 Typed List Retrieval

The Context provides dedicated methods for retrieving lists of a specified element type.

```java
List<String> values = context().getList(
        TestContextKey.MY_KEY,
        String.class
);
```

The method validates that:

- The stored object is a `List`.
- Every non-null element is compatible with the expected element type.

If the key is missing, `getList()` returns `null`.

### 9.2 Required List Retrieval

When a list must exist, use `requireList()`.

```java
List<String> values = context().requireList(
        TestContextKey.MY_KEY,
        String.class
);
```

An overload also supports a custom error message.

```java
List<String> values = context().requireList(
        TestContextKey.MY_KEY,
        String.class,
        "Expected transaction references were not found"
);
```

These methods provide safer access to lists stored in the Context than manually casting objects.

## 10. Scenario Context Lifecycle

### 10.1 Shared Instance

`ApiContext` is instantiated by the Singleton `ServiceClients` class.

The same instance is used by the shared `RestClient` and is available to Step Definitions through `context()`.

### 10.2 Automatic Cleanup

The Context is cleared automatically after each Cucumber scenario.

The cleanup is implemented through an `@After` hook:

```java
@After(order = 501)
public void cleanupContext() {
    context().clear();
}
```

The `clear()` method removes both:

- Recorded API exchanges.
- Additional stored test values.

This ensures that data from a completed scenario is not retained for the next sequential scenario.

### 10.3 Lifecycle Considerations

The Context uses a shared Singleton instance backed by regular Java collections.

The current implementation should not be treated as providing automatic isolation between concurrently executed scenarios.

When using the Context, test implementations should rely on the configured scenario lifecycle and avoid retaining references to data that has already been cleared.

## 11. Practical Example

The following example demonstrates how a Gateway request can be executed, retrieved from Context, and tagged for later use.

```java
import com.barclaycard.systemtest.emv.gateway.api.client.ApiExchange;
```

**Example execution:**

```java
ApiResponse response = GATEWAY()
        .changeTokenOwnerState(tokenOwnerId, request);

assertThat(response.isSuccessful()).isTrue();
```

**Retrieve the latest Gateway operation:**

```java
ApiExchange exchange = context().requireLast(
        ServiceUrls.Gateway.CHANGE_TOKEN_OWNER_STATE
);

ApiResponse storedResponse = exchange.getResponse();
```

**Attach an additional logical tag:**

```java
context().tag(
        ServiceUrls.Gateway.CHANGE_TOKEN_OWNER_STATE,
        MyExchangeTag.CONFIGURATION_UPDATED
);
```

**Retrieve it by the additional tag:**

```java
ApiResponse taggedResponse = context()
        .requireLast(MyExchangeTag.CONFIGURATION_UPDATED)
        .getResponse();
```

The same Context can also store independent test data:

```java
context().put(TestContextKey.MY_KEY, tokenOwnerId);

String storedTokenOwnerId = context().require(
        TestContextKey.MY_KEY,
        String.class
);
```

The stored exchanges and values will be cleared automatically after scenario execution.

## 12. Summary

Scenario Context provides a centralised mechanism for maintaining API execution history and additional test data.

`ApiExchange` preserves request/response pairs and supports multiple logical keys.

`ApiContext` provides convenient methods for accessing the latest exchanges, filtering execution history, tagging operations, and storing typed values.

Automatic integration with `RestClient` reduces the need for manual tracking, while Cucumber lifecycle hooks ensure that stored data is cleared after each scenario.
