
# Centralized Service Access & Singleton Management

## 1. Overview

The EMV & Gateway integration provides a centralised entry point for accessing reusable API service clients and the Scenario Context.

The `ServiceClients` class manages the initialization and reuse of these components through the Initialization-on-demand Holder pattern.

This allows Step Definitions and supporting services to access shared clients without manually creating or configuring their dependencies.

## 2. ServiceClients

**Package:**
`com.barclaycard.systemtest.emv.gateway.services`

The `ServiceClients` class is responsible for creating and exposing the following components:

| Component | Access Method | Responsibility |
|---|---|---|
| ApiContext | `context()` | Stores API exchanges and additional test data |
| EmvService | `EMV()` | Provides access to EMV API operations |
| GatewayService | `GATEWAY()` | Provides access to Gateway API operations |
| EmvActuatorService | `EMV_ACTUATOR()` | Provides access to EMV Actuator endpoints |
| GatewayActuatorService | `GATEWAY_ACTUATOR()` | Provides access to Gateway Actuator endpoints |
| WireMockClient | `WIREMOCK()` | Provides operations for managing WireMock behaviour |

All access methods are static and return previously initialized instances.

### 2.1 Usage

Services can be accessed directly using static imports:

```java
import static com.barclaycard.systemtest.emv.gateway.services.ServiceClients.*;

ApiContext context = context();

EmvService emv = EMV();

GatewayService gateway = GATEWAY();

EmvActuatorService emvActuator = EMV_ACTUATOR();

GatewayActuatorService gatewayActuator = GATEWAY_ACTUATOR();

WireMockClient wireMock = WIREMOCK();
```

There is no need to instantiate these services manually in individual Step Definitions.

## 3. Singleton Initialization

The `ServiceClients` class uses the Initialization-on-demand Holder pattern.

A private static nested class holds the single `ServiceClients` instance:

```java
private static class Holder {
    private static final ServiceClients INSTANCE = new ServiceClients();
}
```

The instance is initialized when the Holder is first accessed.

Subsequent calls to the public access methods reuse the same initialized components.

### 3.1 Shared Dependencies

During initialization, `ServiceClients` creates:

1. A single `ApiContext` instance.
2. A single `ApiLogger` instance.
3. A shared `RestClient` configured with the logger and context.
4. Dedicated EMV, Gateway, and Actuator services.
5. A WireMock client using the EMV Actuator service.

The same `RestClient` instance is reused by the API services and their authorization components.

This ensures consistent HTTP request execution, logging, and Context tracking across supported API operations.

### 3.2 Service Dependencies

| Service | Main Dependencies |
|---|---|
| RestClient | ApiLogger, ApiContext |
| EmvService | RestClient, EmvAuthService |
| GatewayService | RestClient, GatewayAuthService |
| EmvActuatorService | RestClient |
| GatewayActuatorService | RestClient |
| WireMockClient | EmvActuatorService |

Authorization services use the shared REST client while maintaining their respective authentication logic.

## 4. Scenario Context Lifecycle

The `ApiContext` instance is created and exposed by `ServiceClients`:

```java
ApiContext context = context();
```

Although the same instance is reused throughout test execution, its stored data is cleared after each Cucumber scenario.

The cleanup is performed through an `@After` hook:

```java
@After(order = 501)
public void cleanupContext() {
    context().clear();
}
```

The `clear()` operation removes:

- Stored API request/response exchanges.
- Additional values associated with `TestContextKey`.

This allows the same Context instance to be reused across consecutive scenarios without retaining data from previously completed scenarios.

The Context API, exchange history, tagging, and typed data access are described in the **Scenario Context** chapter.

## 5. Database Client Management

Oracle and MongoDB clients are managed separately from `ServiceClients`.

The centralised service access class does not create or expose these database connections.

- **Oracle Database:** Connection management and database operations are handled by the dedicated Oracle integration.
- **MongoDB:** Uses its own lazy Singleton client and connection pool.

The MongoDB client is closed at the end of the test run through an `@AfterAll` hook, using `closeIfInitialized()` to avoid creating a new client solely for cleanup.

Additional details are provided in the **Oracle Database Integration** and **MongoDB Integration** chapters.

## 6. Benefits

Centralised service access provides several advantages:

- A consistent way to obtain API service clients.
- Reuse of shared HTTP infrastructure.
- Centralised request logging and response tracking.
- Automatic dependency initialization.
- Reduced duplication in Step Definitions.
- Clear separation between API service management and database connectivity.

## 7. Summary

`ServiceClients` acts as the main entry point for EMV, Gateway, Actuator, and WireMock API functionality.

It also exposes the shared `ApiContext`, which is automatically cleared after each scenario.

This approach allows test implementations to focus on business operations while service initialization and common infrastructure are managed centrally.
